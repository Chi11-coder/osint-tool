# Go言語 コーディング規約 (2026 Modern Edition)

## 1. 前提方針 (Core Principles)
* **公式標準への準拠:** 本規約は、ベースとなる『[Effective Go](https://go.dev/doc/effective_go)』および公式の『[Go Code Review Comments](https://github.com/golang/go/wiki/CodeReviewComments)』の思想を継承し、近年の言語アップデート（Go 1.18〜1.26+）を反映したものである。
* **ツールによる自動化:** フォーマット（`gofmt` / `goimports`）や静的解析（`golangci-lint`）で機械的にチェックできる内容については、レビュー時に人間が指摘することを禁止する。

---

## 2. 近年の言語仕様に伴う最新ルール

### 2.1 ジェネリクス (Generics / Type Parameters)
* **導入の判断基準:** 原則として、単に「インターフェースによる抽象化」で解決できるケースにジェネリクスを乱用してはならない。データ構造（木構造、キュー、汎用キャッシュなど）や、型に依存しないユーティリティ関数（Sliceのマッピングやフィルタリングなど）を定義する場合にのみ限定して使用すること。
* **型制約（Type Constraints）:** 標準ライブラリの `cmp.Ordered` や `any` を優先して使用し、不必要に複雑なカスタム型制約を定義しない。

### 2.2 Forループ変数のスコープ（Go 1.22以降の最適化）
* **ゴルーチン内での参照:** Go 1.22以降、`for` ループの変数はイテレーションごとに新しいインスタンスが生成される仕様に変更された。そのため、以下のようにゴルーチンやクロージャへループ変数を直接渡しても安全である（過去の `v := v` といった再代入コードは新規実装では原則不要）。
```go
for _, v := range items {
    go func() {
        process(v) // Go 1.22以降はバグにならない
    }()
}
```

### 2.3 new関数による初期化（Go 1.26以降の最適化）
* 値の直接指定: Go 1.26以降、new() の引数に初期値を指定する式を渡すことが可能になった。ポインタ型のプリミティブ値を生成する際、不必要な一時変数の宣言を避け、可読性を向上させるために活用してよい。
```go
// ◯ 推奨（Go 1.26+）
countPtr := new(int64(100))

// 従来の冗長な書き方
// var tmp int64 = 100; countPtr := &tmp
```

## 3. ロギングとエラーハンドリング

### 3.1 構造化ロギング（Structured Logging）
* slogパッケージの強制: サードパーティ製のロギングライブラリ（zap, logrus等）の新規導入は避け、標準ライブラリの log/slog を使用すること。  

* コンテキストの伝播: ログには必ず context.Context を伝播させ（Logger.InfoContext 等の利用）、トレースIDなどが自動出力されるように設計する。

### 3.2 エラーのラップと判定
* Error Wrapping: エラーを上位レイヤに返す際は、元のエラー文脈を維持するために %w 形式でラップする
```go
return fmt.Errorf("failed to process user: %w", err)
```
* 判定方法: エラーの型判定や値の比較には、直接 == や型アサーションを使用せず、必ず errors.Is または errors.As を使用する

## 4. 並行処理 (Concurrency)

### 4.1 ゴルーチンのライフサイクル管理
* リークの防止: ゴルーチンを開始する際は、それが「いつ、どのように終了するか」が明確でなければならない。

* Contextの必須化: 外部API通信、DBアクセス、非同期処理を行う関数は、第一引数に必ず ctx context.Context を受け取り、キャンセルシグナル（ctx.Done()）を適切にハンドリングすること。

### 4.2 チャネルとMutexの使い分け
* チャネルの用途: データの所有権の移転や、パイプライン処理、シグナリング（同期）にはチャネルを使用する。

* Mutexの用途: 構造体内部の単純な状態（カウンターやキャッシュマップなど）の一貫性を保護するローカルな排他制御には、sync.Mutex や sync.RWMutex を使用する（Effective Goの思想に基づき、過度な「チャネルによる排他制御」でコードを複雑にしない）。
